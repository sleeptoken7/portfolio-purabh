# Healthcare Code Resolver Pipeline

## Problem Statement
This project built a privacy-first pipeline that maps article text to official medical codes from the authoritative medical classification dataset. The original service appended every candidate URL to an external LLM processing queue; this caused high costs, frequent duplicates, and data leaving the organization.

The new approach reduces external API dependency, prevents duplicate work, and provides a fast, deterministic resolution path suitable for offline deployment.

## Approach Overview

*   Use a lightweight content pre-filter to block non-medical pages and only send high-confidence medical content to the local extractor model.
*   Build an efficient local resolver using SQLite + FTS5 against the official medical-classification dataset.
*   Maintain a domain memory cache and a small feedback engine to reduce repeated work and improve resolution throughput over time.

### Local-first Resolution
The pipeline relies on a local, quantized extractor model running on CPU and a deterministic, tokenised search over the official medical-classification dataset. This combination provides low-latency, auditable outputs and removes the need for per-call cloud LLM expenses.

### Efficiency Gains
By pre-filtering content and using domain memory, the system reduces expensive model invocations by over 80% while preserving high recall for medical content.

## The Intelligence Layer — Why It Matters
The intelligence layer is the architectural decision that separates this from a simple ETL pipeline.

*   **The Content Filter.** A typical Beeswax log contains URLs from hundreds of domains — news, sports, finance, entertainment, and health all mixed together. Running the LLM on every URL regardless of content is wasteful. The `ContentFilter` scans article text against a curated medical vocabulary before any LLM call is made. If fewer than the minimum threshold of medical terms are found, the article is classified `non_medical` and skipped entirely. In practice this eliminates approximately 86% of LLM calls with zero false negatives on genuine medical content.
*   **Domain Memory.** Web crawlers regularly encounter bot detection, Cloudflare blocks, and dead links. Without memory, the pipeline retries blocked domains on every single run. `DomainMemory` records the outcome of every domain crawl and uses it to short-circuit future attempts. A domain that returned a 403 will be marked `blocked (cached)` on the next run without making a network request.
*   **The Feedback Engine.** The same medical entities appear repeatedly across thousands of health URLs — "diabetes", "hypertension", "influenza" appear in every health log. Without a learning mechanism, each occurrence goes through the full resolution pipeline independently. The `FeedbackEngine` records successful entity-to-code mappings and builds a knowledge base that grows richer with every run.

## Medical-classification Resolver — Technical Design
The resolver uses a four-step strategy with explicit fallback:

```text
Entity input
    │
    ├─► Synonym normalisation      "heart attack" → "myocardial infarction"
    │   + Spelling normalisation   "haemorrhage"  → "hemorrhage"
    │
    ├─► Step 1: Direct code match  If input looks like "J10.1" → exact lookup, score 1.0
    │
    ├─► Step 2: FTS5 search        Tokenise, strip hyphens (FTS5 treats "-" as NOT operator),
    │                              build prefix queries: "myocardial* infarction*"
    │                              Score by token overlap + substring containment boosts
    │
    ├─► Step 3: Substring fallback  LIKE %query% against 294,558 normalised terms
    │
    └─► Step 4: Abstain            score < 0.45 → unresolved, logged for review
```

*   **Why FTS5 and not a vector database?** ICD-10 codes have canonical, deterministic descriptions. The matching problem is not semantic similarity — it is lexical precision. FTS5 prefix search on a well-normalised term table outperforms vector similarity for this use case, runs in microseconds, requires no GPU, and introduces no probabilistic uncertainty.
*   **Why synonym maps instead of relying on the LLM to output ICD-canonical terms?** LLMs extract the language of the article, written for general audiences. Articles say "heart attack", "stomach flu", "shingles". ICD-10 says "myocardial infarction", "infectious gastroenteritis", "herpes zoster". The synonym map is a deterministic, auditable bridge between these two vocabularies — zero latency, zero failure modes.

## Output Fields

| Field | Description |
| :--- | :--- |
| **source_row** | Original row number from the input spreadsheet (used for resume and tracing). |

## How to Run (Server)

### 1. Start everything
```bash
ssh ubuntu@<server-ip>
cd ~/llmOps/llm-lab
make up
```
Then open `http://<server>:8001` and click a model to load it.

### 2. Upload input spreadsheet
Open `http://<server>:8000/upload` in a browser. The file must be `.xlsx` with a column named exactly `page_url`. Extra columns are ignored. The page validates the file before saving and shows the active input and last-run summary at all times.

### 3. Run the pipeline
```bash
make run N=50    # process 50 URLs
make run N=all   # process all rows
```

Results are written to SQLite and immediately queryable:
- `http://<server>:8000/results?has_icd=true` — rows with ICD codes
- `http://<server>:3333/traces` — Langfuse trace viewer with token counts

The pipeline is fully resumable — stop at any point, re-run, it picks up from the last checkpoint with domain memory preserved.
