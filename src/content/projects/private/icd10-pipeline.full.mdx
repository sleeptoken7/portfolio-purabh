# AdPrime ICD-10 Intelligence Pipeline

## The Problem We Were Solving
AdPrime's core value proposition is matching digital advertising inventory to the right medical audiences. To do that well, we need to understand what health topic a given URL is about — not just loosely ("this is a health article") but precisely, in the clinical language that the industry actually uses: ICD-10 codes.

The existing system had a working pipeline: crawl a URL, extract text, send it to a cloud LLM, get medical entities back, look them up in a code table. It worked. But it had two critical limitations.

*   **Limitation 1 — The cloud LLM was a dependency.** Every article processed made an API call to an external LLM provider. This meant rate limits, quota costs, data leaving the organization, and a hard dependency on internet connectivity and third-party uptime.
*   **Limitation 2 — The pipeline had no memory or intelligence.** Each run was stateless. If a domain had been crawled and blocked by Cloudflare yesterday, the pipeline would try it again today. If "norovirus" had been resolved successfully a hundred times, it still did the same full lookup on run 101. There was no accumulation of knowledge.

## The Approach
Rather than patch the existing system, we took a research-first approach: understand what was limiting accuracy, find the authoritative data source, and redesign the resolution layer from scratch.

*   **Finding 1:** The CDC publishes the complete ICD-10-CM code set annually as a flat text file. The FY2026 release contains 98,186 codes with full short and long descriptions. This is the ground truth used by every hospital, insurer, and billing system in the United States. Using anything else is inherently incomplete.
*   **Finding 2:** SQLite with FTS5 (full-text search) can run 98,186-code lookups in under 5ms on commodity hardware, with zero external dependencies. There is no reason to pay for a vector database or external search API for this use case.
*   **Finding 3:** Open-source instruction-tuned (Small Language Models) in the 2-4B parameter range, quantized to Q4/Q6 precision, run at acceptable speeds on CPU-only hardware and are sufficient for structured entity extraction tasks. We benchmarked several options.

### Why This Model
The local LLM selected is **numind/NuExtract (Q4_K quantization, GGUF format)**, running via on CPU.

### The Benchmarking Decision
Models were evaluated on two axes: entity extraction accuracy and structured JSON output reliability.

### Why ContentFilter first?
Beeswax logs contain mixed content — sports, finance, entertainment alongside health. Running LLM on every URL wastes compute. The `health_vocab.txt` pre-scan:
*   Checks for medical keywords before any LLM call
*   Saves ~86% of LLM tokens on non-medical articles
*   Zero false negatives on genuine medical content

The ContentFilter doesn't do any "AI." It uses a simple, high-performance programming technique called **String Matching**.

1.  **The Dictionary:** We have a file called `health_vocab.txt` with ~120+ words (e.g., patient, surgery, cardiology, symptoms, chronic).
2.  **The Scan:** It takes the article text and counts how many words from our dictionary appear in it.
3.  **The Threshold:** We set a rule: "If fewer than 3 of these words appear, this is likely not a medical article."
4.  **The Result:**
    *   **Pass:** If it finds "heart," "valve," and "surgery," it sends it to the LLM.
    *   **Fail:** If it's an article about a "football match" and it finds 0 medical words, it marks it as `non_medical` in your Excel sheet and stops right there.
